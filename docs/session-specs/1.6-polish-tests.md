## Polish scope
1. Loading states: skeleton screens (not spinners) matching content shape — 5 combinations: Views list/detail/create/edit, plus Topics list. Topics detail/create/edit pages don't exist yet (deferred to Session 1.6a) and are excluded from this count.
2. Error states: failed fetch, failed save, not-found, unauthorized — same 5 page/entity combinations
3. Empty states: "No Views yet" / "No Topics yet"
4. Delete UI + confirmation dialog — Views and Topics. No delete button existed in the UI prior to this session (verified via grep); backend delete was RLS-protected but unreachable from the app.
5. ~~Dark-mode check: contrast, destructive buttons, validation messages, focus outlines, disabled submit-button state.~~ Deferred to backlog — not part of today's DoD. Toasts and badges considered and confirmed not applicable (don't exist in the app, verified via grep).
6. Form-state preservation on failed save: verified already correct in new-view-form.tsx — each field is independent React state, never reset on failure. No action needed, documented here for completeness.

## Test scope
7. Five tenancy tests — on review, 4 of these 5 already exist in tests/rls-tenancy.test.ts with the user labels swapped (RLS policies are symmetric between any two users, so "user B cannot UPDATE user A's X" exercises the identical policy code path as "user A edits user B's X" — relabeling would be a duplicate, not new coverage). Only the last one is genuinely new:
   - User A edits user B's View → fails — already covered: tests/rls-tenancy.test.ts:493 ("user B cannot UPDATE user A's view")
   - User A deletes user B's View → fails — already covered: tests/rls-tenancy.test.ts:343 ("user B cannot delete user A's view")
   - User A edits user B's Topic → fails — already covered: tests/rls-tenancy.test.ts:477 ("user B cannot UPDATE user A's topic")
   - User A deletes user B's Topic → fails — already covered: tests/rls-tenancy.test.ts:329 ("user B cannot delete user A's topic")
   - Unauthenticated access to any Views/Topics route → fails — genuinely new, added in tests/middleware-auth.test.ts. Different layer than the rest of the suite: this is lib/supabase/middleware.ts's redirect-to-/login gate, not Supabase RLS, so it unit-tests updateSession() directly against a hand-built NextRequest rather than going through a Supabase client.
8. view_topics cross-tenant insert test: user A cannot link their View to user B's Topic. Already satisfied — added in the Session 1.5 commit, before this spec was written: tests/rls-tenancy.test.ts:268 ("user A cannot insert a view_topics row linking their view to user B's topic"). Verified against the actual RLS policy (20260803140000_scope_rls_policies_per_operation.sql) — already two-sided (EXISTS checks on both views and topics ownership), not a live vulnerability, but view_topics has a real UI surface (Topic assignment on View create/edit) so it was worth testing. No new test needed.
