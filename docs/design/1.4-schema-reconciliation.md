# Design Note: Session 1.4 Schema Reconciliation

See [ADR-003](../adr/ADR-003-prd-schema-reconciliation.md) for the full decision record. This note summarizes the resulting data model in plain terms.

## Why this happened

Session 1.3's migration had drifted from both `docs/PRD.md` §6 and `docs/tech-design.md` §3 in seven undocumented ways. This surfaced while seeding real test data in Session 1.4 — the empty `/views` page couldn't be explained by data alone. None of the drift had been logged as an ADR, despite CLAUDE.md's own convention requiring one for non-obvious decisions.

## What changed

- **PRD.md is now the baseline** for all data-model questions when it conflicts with `tech-design.md` or the deployed schema.
- **views.hypothesis** dropped (no PRD lineage).
- **topics.description** renamed to **topics.framing_note** (matches PRD §6).
- **views.confidence** renamed to **confidence_level**, constrained to `low` / `medium` / `high`.
- **views.time_horizon** constrained to `<1yr` / `1-3yr` / `3-10yr` / `10+yr` / `unclear`.
- **views.tags** added (free text, per PRD §7).
- **view_relationships** columns renamed `view_id_a`/`view_id_b` → `view_id`/`related_view_id`, with a canonical-order CHECK (`view_id < related_view_id`) replacing the old no-self-link check — this also prevents a duplicate inverse row for the same pair.
- **evidence_items redesigned to many-to-many with views**, via a new `view_evidence` join table — replacing the single `view_id` FK (one-to-many). This matches a real workflow gap: one piece of evidence (e.g. a single article) often covers multiple Views or Topics at once, and the old schema forced duplicate rows to cover overlapping theses.
  - `evidence_items` gained a direct `user_id` column (owner), replacing the old single-sided EXISTS-via-`view_id` RLS check — necessary because an evidence item can now exist with zero linked views.
  - `view_evidence` uses two-sided RLS (EXISTS checks against both the owned `views` row and the owned `evidence_items` row), same pattern as `view_topics`.
  - `link`, `note`, and `stance` (renamed from `content`/`source_url`/`supports_or_contradicts`) are all optional — an evidence item may exist with only a stance, or only a link, or only a note.
  - No DB-level constraint requires an evidence_items row to have at least one linked View — enforced at the application layer only, consistent with the existing "a View needs ≥1 Topic" rule, and deliberately leaves room for a deferred Topic-first-then-route workflow.
- **"Title" stays the column name on views** — JT's mental model is "thesis title," but this was treated as a UX/labeling decision (form and detail-page copy), not a schema rename.
- **Seeded the three real Parchmount Views** from the PRD appendix as actual data, for the first time.

## What this doesn't cover

This was a schema-only change. No evidence-capture UI was built in Session 1.4 — `evidence_items` and `view_evidence` existed only as tables with no app-level CRUD until later sessions.

## Addendum: Session 1.6 stance expansion (deferred to 1.6b)

`stance` is currently a two-value CHECK constraint (`for` / `against`), set by the migration above. Session 1.6's polish/test spec (`docs/session-specs/1.6-polish-tests.md`) locked in a decision to expand this to three values — `for` / `against` / `context` — but implementation is deferred to Session 1.6b, along with evidence CRUD itself (no UI exists yet to expand).

Still open, deferred as ADR-level pre-work at the start of 1.6b: whether `stance` belongs on `evidence_items` (per-item, current schema — one stance regardless of which View it's linked to) or on `view_evidence` (per-link — the same evidence item could support one View and contradict another). This wasn't resolved in Session 1.4 and hasn't been resolved since; it needs a decision before 1.6b's evidence CRUD UI can be built against a stable schema.
